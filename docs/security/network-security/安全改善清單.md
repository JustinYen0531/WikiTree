# WikiTree Supabase 安全改善清單

以下依風險和處理順序排列。前四項可從 repo 的 SQL 與前端程式確認；Supabase `nccu hub` 專案目前是 `INACTIVE`，實際線上 schema 和權限仍待重新連線後核對。

## 1. 停止在 Supabase 複製或取回明文密碼（最高優先）

- **白話原因：** 系統現在把使用者原本的登入密碼另外存一份，忘記密碼時還會把它顯示出來。只要這份資料或找回流程被拿到，別人的帳號就可能被登入。
- **改善方向：** 移除 `recovery_password` 和「答對提示問題就顯示原密碼」的流程，改用 Supabase Auth 的密碼重設流程。提示答案也不再作為取回密碼的方式。
- **完成標準：** Supabase 新註冊不再把密碼複製到 `user_security`；忘記密碼只能走 Supabase Auth 的重設流程；舊雲端密碼副本有明確清除方案。本機 `localStorage` 的帳號密碼另列第 2 項，依序處理。
- **狀態：** 程式和 migration 已準備；待資料庫恢復連線後套用 migration 並確認刪除舊副本。
- **注意：** 密碼重設信需能寄到帳號對應的學校信箱，且 Supabase Auth 的重設 redirect URL 必須允許 WikiTree 網址。Supabase 預設寄信服務可能限制收件人；若一般使用者收不到信，需要先設定自訂 SMTP。

## 2. 停止在瀏覽器本機明文保存密碼

- **白話原因：** Supabase 沒設定時，另一條登入路徑會把密碼和提示答案放進瀏覽器 `localStorage`。使用同一台電腦的人或有權讀取瀏覽器資料的程式可能看見它們。
- **改善方向：** 移除這種明文本機帳號保存；若需要離線模式，採用不保存原始密碼的登入設計，並清理既有本機資料。
- **完成標準：** 本機儲存不含密碼或提示答案；未設定 Supabase 時，介面清楚說明登入不可用或提供安全的替代方式。
- **狀態：** 待改善。

## 3. 移除可探測帳號的提示問題查詢

- **白話原因：** 只輸入帳號就能查到提示問題；有人可以逐一試帳號，確認哪些人註冊過。這項功能也會隨密碼提示流程一起失去必要性。
- **改善方向：** 移除 `get_user_hint_question` RPC 及前端呼叫，讓忘記密碼流程使用 Supabase Auth，不回傳帳號提示資料。
- **完成標準：** 未登入者無法用 RPC 查帳號提示問題；前端忘記密碼流程不再呼叫此函式。
- **狀態：** 待改善。

## 4. 核實並收緊資料表與 RPC 權限

- **白話原因：** RLS 像每張表的門禁；`SECURITY DEFINER` 函式則可能用資料庫管理員權限替呼叫者開門。必須確認每個角色實際能讀寫哪些資料。
- **改善方向：** 資料庫恢復連線後盤點 tables、policies、grants 和函式執行權限；只開放產品真正需要的操作。任何保留的高權限函式都要限制呼叫者與可操作資料。
- **完成標準：** 每張公開 schema 的表都啟用 RLS；權限符合登入者自己的資料範圍；不需要的函式已移除或撤銷公開執行權限；用不同角色實際確認允許和拒絕的操作。
- **狀態：** 待資料庫重新連線後盤點。

## 5. 把 SQL Editor 腳本改成可追蹤、可重複部署的 migration

- **白話原因：** 手動貼 SQL 不容易知道哪個版本已經執行；目前的表格建立語句可重跑，但建立 policy 的語句可能因已存在而中斷。
- **改善方向：** 將整理後的 schema 變更存成 repo migration，記錄用途和順序；部署前核對目前線上 schema，避免把已存在的變更再套一次。
- **完成標準：** repo 有完整 migration；每次部署都能查到執行版本；從乾淨環境建置與對既有資料庫升級都有清楚步驟。
- **狀態：** 待改善。

## 6. 核對公開筆記的可見與編輯規則

- **白話原因：** 公開筆記預期任何人可讀，但目前腳本只明確寫了發布與刪除規則。需要確認使用者能否編輯自己的筆記，以及能否改掉作者或公開狀態等欄位。
- **改善方向：** 對照產品需求決定公開/私人筆記的讀取範圍、作者可做的新增/編輯/刪除操作，再為每種操作設計 RLS 條件。
- **完成標準：** 筆記作者只能修改自己的資料；未授權者不能竄改作者、可見性或內容；公開讀取行為符合產品設計。
- **狀態：** 待需求與資料庫現況核對。

## 7. 整理個人資料的公開範圍

- **白話原因：** `profiles` 目前允許任何人讀取整筆資料，欄位包含學院、系所和年級。這可能比顯示作者名稱所需的資料更多。
- **改善方向：** 確認哪些個人資料需要公開；只公開必要欄位，或用受控 view 提供作者顯示資料。
- **完成標準：** 公開介面只拿得到必要欄位；其他個人資料不能透過 API 任意查閱。
- **狀態：** 待需求與資料庫現況核對。

## 建議逐項處理順序

先處理第 1 項，再處理第 2、3 項，接著重新連上資料庫完成第 4 項盤點。盤點結果確認後才建立第 5 項 migration，最後依產品需求處理第 6、7 項。每一步先看清現有資料與呼叫端，再改程式或 schema，避免只刪掉 SQL 卻讓登入功能壞掉。
